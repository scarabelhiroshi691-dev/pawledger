# 会员储值账务规则

## 1. 设计原则

余额不是允许用户编辑的普通字段，而是已生效资金流水的结果。系统可以保存余额快照来提高查询速度，但每次交易后都必须校验快照与流水汇总一致。

交易需要满足以下不变量：

1. 本金余额与赠送金余额均不得小于零。
2. 一张业务单据的财务结果要么全部提交，要么全部失败。
3. 每个外部请求标识只能产生一次财务结果。
4. 已入账流水不可修改或删除；纠错只能追加反向流水。
5. 退款累计金额不得超过原交易可退金额。
6. 日结不能改变历史流水，只能记录当日汇总快照和差异。

## 2. 账户余额

账户展示三个值：

- 本金余额：会员实际充值后尚未消费或退款的金额。
- 赠送金余额：门店赠送后尚未消费或撤销的金额。
- 可用总额：本金余额 + 赠送金余额。

所有金额使用十进制定点类型，精确到分；数据库内禁止使用二进制浮点数表示金额。

## 3. 流水方向与类型

每条流水只影响一个资金桶，即本金或赠送金。金额使用带符号值：增加为正，扣减为负。

建议的业务类型：

- 充值本金
- 充值赠送
- 消费本金
- 消费赠送
- 消费退款本金
- 消费退款赠送
- 充值退款本金
- 充值赠送撤销
- 管理员冲正
- 期初余额导入

每条流水必须包含会员账户、业务类型、资金桶、金额、发生时间、业务单据、原流水引用、操作人和幂等请求标识。

## 4. 消费分摊示例

交易前：本金 1,000 元，赠送金 100 元。应付 180 元。

1. 赠送金扣 100 元。
2. 本金扣 80 元。
3. 交易后：本金 920 元，赠送金 0 元。

如应付 1,200 元，则赠送金扣 100 元、本金扣 1,000 元，剩余 100 元必须由外部支付方式补足，否则不能完成结算。

## 5. 消费退款示例

上例 180 元美容服务全额退款：

- 追加赠送金 +100 元的退款流水。
- 追加本金 +80 元的退款流水。
- 美容订单退款金额增加 180 元。
- 美容师净业绩减少 180 元。

部分退款按照原交易资金构成分配。首版采用“按原扣款顺序反向恢复”的确定性算法，退款结果在确认前展示，避免店员自行选择资金桶造成对账差异。

## 6. 充值退款

充值退款风险高于消费退款，必须由管理员执行：

1. 选择原充值单。
2. 系统计算该充值仍可退的本金和仍可撤销的赠送金。
3. 若相关资金已经消费，系统拒绝直接退款，并列出关联消费。
4. 确认后追加本金负向流水和赠送金负向流水，记录线下退款方式。
5. 不得删除或覆盖原充值流水。

## 7. 事务边界

以下内容必须在同一 SQLite 事务中完成：

- 锁定并校验会员账户版本。
- 校验余额、原单可退金额和幂等标识。
- 写入订单/退款单状态。
- 写入会员资金流水。
- 更新余额快照与版本号。
- 写入支付明细、业绩变化和审计日志。
- 提交前重新检查余额不变量。

发生异常时整个事务回滚。界面只能在服务端事务提交成功后显示“结算成功”。

## 8. 防重复与审计

- 充值、结算和退款请求均由客户端生成唯一请求标识。
- 数据库对请求标识建立唯一约束。
- 重复请求返回第一次处理结果，不重复入账。
- 财务单据使用不可猜测的公开编号和内部主键。
- 审计日志记录操作前后关键状态，但不得记录密码等敏感信息。

## 9. 对账检查

每次日结和应用启动后执行快速检查：

- 账户快照是否等于流水合计。
- 是否存在负余额。
- 是否存在已结算订单但缺少支付或会员流水。
- 是否存在退款超过原交易的情况。
- 是否存在孤立流水或重复请求标识。

发现异常时进入只读财务保护状态：允许查询和导出，暂停新的充值、消费和退款，直到管理员备份并完成诊断。
